Probabilistic reasoning inside. Logical guardrails outside.
01 · The problem

An agent is an LLM, some tools and a loop. That loop has almost no brakes.

Most agent failures, from brittle tools to fragile handoffs, drift and infinite loops, are symptoms of one missing layer: an explicit model of the domain sitting outside the model.

Turing-complete

The loop can do anything, including never stop. No type checker fully covers a program that writes its own next step.

Probabilistic

Every step is a sample, not a decision. Hallucination is a feature: imagining plausible continuations is what a next-token model is for.

One JSON check

Between "the model proposed a tool call" and "the tool ran" there is usually nothing but a schema check on the arguments.

while True: resp = llm(messages, tools) if resp.stop_reason == "end_turn": break for call in resp.tool_calls: validate(call.args) # JSON schema only result = execute(call) # side effects happen here messages.append(result)

When an agent issues a duplicate refund, it is not malfunctioning

It is doing exactly what it was built to do: generate the most probable next sequence of tokens. A paragraph of instructions ("only use valid statuses") cannot reliably stop a sampler from sampling something else. The fix is a layer that can say no.

03 · What an ontology is

"Data as graphs": every fact is a triple

Subject → predicate → object. Triples compose into a knowledge graph. The schema layer (classes, properties, constraints) is the ontology; the instance layer is your data.

:Alice a :Customer :Order_123 a :Order :Order_123 :placedBy :Alice :Order_123 :hasStatus :Shipped :Refund_9 a :Refund :Refund_9 :refunds :Order_123 :Refund_9 :paidTo :Alice :Bob a :SupportRep

04 · The toolkit

A few declarations turn a graph into a rule-checker

RDFS gives you inference for free. OWL adds the constraints that catch real business errors. None of it is new: it is W3C-standard tooling.

RDFS domain / rangedeclaring what a property connects lets a reasoner type both ends:teaches domain :Teacher, range :Student

05 · The pattern

Pydantic at the door, ontology at the ledger

Two different checks for two different problems. Type checking answers "is this well-formed?". The ontology answers "is this true and allowed in our world?".

caught by the ledger

Duplicate refund

:Refund_9 :refunds :Order_123 already exists. A second refund violates the cardinality rule. Pydantic sees two perfectly valid calls.

caught by the ledger

Misdirected payout

The payee is typed :SupportRep. Customer and SupportRep are disjoint. A payout to the rep is a logical violation, not a style issue.

caught by the ledger

Invented status

"probably shipped" is a fine string and a valid JSON value. It is not in the enumerated range of :hasStatus, so it is rejected.

06 · Building it

Top-down and bottom-up

Top-down

Domain experts define the core classes, properties and rules up front. Precise and explicit. Also exactly what 1980s expert systems did, and hand-building everything did not scale.

Bottom-up

Extract entities and relationships from real data (tickets, documents, customer interactions) with named-entity recognition and relation extraction, increasingly with LLMs doing the extracting.

In practice: both

Experts seed the business concepts. Observed interactions keep revealing new entities and relations, and the schema is revised as new kinds of things show up.

07 · The architecture

Four layers, one job each

1
LLMinterprets intent, proposes actions · probabilistic
2
Typed interface · Pydantic / JSON schemaconstrains inputs: structure, types, required fields
3
Toolsperform execution · the side effects live here
4
Ontology + reasonerchecks domain consistency before an outcome is accepted · deterministic

Why the split works

The probabilistic part is allowed to be creative: it interprets messy intent and proposes. The deterministic part never has to be creative: it only has to check a proposal against an explicit model of what exists and what is allowed. Neither can do the other's job.

Start small. A handful of classes, a few domain/range declarations, one disjoint pair and one cardinality rule already catch the expensive mistakes.

08 · Takeaways

Five things to remember

  1. Most agent failures share one cause. Brittle tools, fragile handoffs, drift and loops are symptoms of a missing explicit domain model outside the model.
  2. Hallucination is a feature. A sampler samples. Do not fight it with longer prompts; wrap it with a layer that can refuse.
  3. Ontologies are old and standardized. Aristotle to W3C. RDF, RDFS, OWL and SPARQL already exist; you do not have to invent the tooling.
  4. Pydantic at the door, ontology at the ledger. Type-check inputs; semantically check outcomes before any side effect is committed.
  5. Build it both ways. Experts seed the schema, data grows the graph, and the schema is revised as the world turns out to be bigger than the spec.
